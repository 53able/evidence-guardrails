# 要求から検証証拠へ追跡する

## 手順

1. 新規プロジェクトまたは変更の目的、関係するステークホルダー、制約を抽出する。目的が不明なら要求を発明せず、確認質問として記録する。
2. `assets/traceability-table-template.md` を複製する。`N-*`、`R-*`、`D-*`、`V-*` を後続のV&V証拠表でも同じIDとして使う。
3. ニーズを「なぜ必要か」、要求を「何が観測できれば満たすか」、設計判断を「どの実現方法を選ぶか」として別々に記録する。
4. 各要求に、少なくとも一つの検証方法と、実行済みなら証拠の場所・コマンド・結果を結ぶ。
5. 設計判断だけでニーズや要求を満たしたと扱わない。要求なしの新規プロジェクトまたは変更は `unverified`、根拠がない項目は `unknown` とする。
6. `references/quality-rules.md` を読み、要求と設計または計画と結果を混同していないか確認する。
7. `scripts/validate-traceability.py <追跡表ファイル>` を実行する。失敗時は、要求、検証方法、状態の欠落を修正するか `blocked` として残す。
8. 要求別に、証拠済み、未実施、blocked、残余リスクを出力する。

## 出力規約

- 「テスト予定」は証拠ではない。
- 実装詳細を要求として書き換えない。ただし制約として明示された実装指定は区別して残す。
- 実行していない検証は `not run` と書く。

## Error Handling

- 要求の根拠が資料にない場合は、ステークホルダー確認を依頼し、推測した要求を作らない。
- 検証手段が存在しない場合は、要求を満たしたと宣言せず、検証設計の作業として切り出す。
